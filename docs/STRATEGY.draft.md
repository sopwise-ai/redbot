# RedBot 定位与战略 v2（草案）

> v1 是「给中文网民的一页热榜按钮」。v2 按你的新方向重写：**线上、中文、办公人群、PC 优先、
> 共享成千上万个站点、解决「不知道去哪找」**。
>
> 参考对象：[usemagpie.ai](https://usemagpie.ai/)（AI 本地网关）。它不是同类产品，但它的**产品叙事手法**
> 值得整套搬过来，第 3 节拆了六条。
>
> 仍然按「现状 → 判断 → 待你拍板」组织。第 10 节是五个必须你定的问题，其余地方你可以直接改字。

## 0 这一版改了什么

| 维度     | v1（现在线上这套）           | v2（你的新方向）                              |
| -------- | ---------------------------- | --------------------------------------------- |
| 用户     | 泛中文网民，扫一眼热榜       | **办公人群**，每天在 PC 上完成具体工作        |
| 价值     | 快 —— 一个按钮直达榜单       | **找得到 + 管得住** —— 不知道去哪找时也能找到 |
| 规模     | 189 条精选，单类硬顶 20      | **万级**，分层（精选 / 收录 / 长尾）          |
| 形态     | 网页（移动端调得比桌面更细） | **网页 + PC 常驻入口**（新标签页 / 扩展）     |
| 记忆     | 足迹（被动记录点过什么）     | **我的**（主动固定、分组、备注、可导出）      |
| 商业模式 | 未定义                       | 未定义（但 v2 的规模必须回答「谁出钱」）      |

## 1 新定位

### 三个候选一句话（选一个，或改）

- A：**上班要用的网站，一个地方找齐。**
- B：**不用记住网址的互联网。**
- C：**你想到要做的事，和你该去的网站之间，只差一次点击。**

我倾向 **A**：它把「办公人群」写在脸上，且「找齐」暗示了目录规模，不与「很快」绑死。
B 更性感但容易被理解为浏览器功能。C 是 A 的解释，适合放副标题。

### 电梯稿

> 办公时要用的网站有几千个，但你脑子里只装得下十几个。RedBot 把「我要做某件事，该去哪个网站」
> 变成一次输入或一次点击：按任务找、按主题找、按你固定过的找。找到之后它留在你的「我的」里，
> 下次不用再想。不做内容聚合，只负责把你和网站连起来。

### 不是什么（红线，继承 v1）

- 不抓取、不展示标题、不存正文（跳走就是全部价值）
- 不做阅读器、不做内容社区、不做推荐流
- 不卖位置、不做商业置顶

## 2 用户与真实痛点

你把痛点说得很准，我把它拆成三层 —— **这三层需要三种不同的产品能力，混在一起就会做成 hao123**：

| 层  | 用户的处境                         | 他现在的做法           | 需要的产品能力                   |
| --- | ---------------------------------- | ---------------------- | -------------------------------- |
| 1   | **脑子里没印象**：不知道存在这个站 | 用 AI 问、用搜索引擎撞 | 任务/场景入口 + 高质量的分类结构 |
| 2   | 有印象，但想不起名字               | 翻收藏夹、翻历史记录   | 模糊搜索（拼音、别名、同义词）   |
| 3   | 想得起，但懒得每次重找             | 存书签，然后书签烂掉   | 「我的」：固定、分组、备注、导出 |

现在这套产品只解了第 1 层的很小一部分（17 个主题 × 20 条），第 2、3 层基本没有。
**足迹只解了第 3 层的一半**：它是被动的（点过什么），而用户真正要的是主动的「这是我常用的」。

### 办公人群为什么会用

办公场景的信息行为是**任务驱动**的，不是兴趣驱动的：

| 场景           | 现在怎么做                   | 卡在哪                     |
| -------------- | ---------------------------- | -------------------------- |
| 做一份行业分析 | 搜「XX 行业 报告」，翻前几页 | 不知道有哪些数据源是权威的 |
| 找配图 / 素材  | 想到哪个用哪个，或问同事     | 好用的站想不起来           |
| 查一家公司     | 天眼查、企查查、官网各试一遍 | 每次都要重新决定去哪       |
| 找模板 / 格式  | 百度文库、WPS、Notion 乱撞   | 不知道还有更专业的         |
| 学一个新工具   | 官方文档 / B 站 / 少数派     | 不知道哪个值得读           |

这些场景的共同点：**用户知道「我要做什么」，但不知道「该去哪」**。
这就是 RedBot 唯一要回答的问题。

### 为什么是 PC 优先

- 办公人群的高价值时段在桌面浏览器里，一个键盘就能完成「输入 → 选中 → 打开」。
- PC 有**常驻位**（新标签页、书签栏、扩展），移动端没有对应物。省时的前提是「不用想起来打开它」。
- 现有产品在移动端花的功夫（抽屉、2 列布局）在 v2 里要退到第二位，键盘流、多列、密度要重新排。

## 3 从 magpie 借什么

magpie 的产品页几乎是这个品类的教科书。**能搬的是叙事结构，不是界面**：

| magpie 的手法                               | RedBot 的对应物                                                  |
| ------------------------------------------- | ---------------------------------------------------------------- |
| 「Every agent's model. One place.」N×M 压缩 | 「N 个网站 × M 件事 → 一个入口」：把「找站」从每次重做变成一次   |
| 一张机制图（agents → gateway → providers）  | 一张「你 → RedBot（任务/主题/我的）→ 网站」的图，放在首屏第二屏  |
| 每个功能都回答「解决什么」，再讲机制        | 每条能力标题写结果（「想不起名字也能搜到」），下面三行讲怎么实现 |
| 信任块：native / tiny / MIT / free          | 纯静态 / 无跟踪 / 开源 / 不卖位置 —— 四句话，可验证              |
| Profiles（Budget / Focus 一键切换）         | **场景包**：把一组站点存成「找素材」「写周报」，一键切换         |
| 下载 + CLI + 菜单栏，三个入口同一套数据     | 网页 + 新标签页 + 浏览器扩展，三个入口共享同一份「我的」         |

其中**两个**我认为必须抄：

1. **N×M 压缩的一句话**。现在 README 讲的是「一个按钮直达一个源」，讲的是「快」；v2 要讲的是
   「几千个网站里，那个你没想到但正需要的」—— 讲的是**覆盖面 + 可检索**。
2. **「一次添加，处处可用」的心智**。magpie 的用户动作是「add a provider once」；
   RedBot 的用户动作应该是「固定一个站 once，之后它在你所有入口里都在」。

## 4 产品结构：三层，不要混

| 层     | 回答的问题           | 形态                                   | 现有资产的处置                     |
| ------ | -------------------- | -------------------------------------- | ---------------------------------- |
| 发现层 | 「我要做 X，去哪？」 | 任务入口 + 全站搜索 + 万级目录（分层） | 现有 17 主题保留为其中一维         |
| 管理层 | 「我常用的在哪？」   | 我的：固定 / 分组 / 备注 / 导入导出    | 足迹升级为「我的」的一个视图       |
| 直达层 | 「就这几个站」       | 现在的按钮墙，收缩为「精选」           | 现有 UI 几乎不用改，定位改成精选层 |

关键判断：**按钮墙不该承载一万条**。一百多条的按钮墙是美感，一万条的按钮墙是灾难。
所以 v2 的首页应该是「搜索框 + 任务入口 + 我的」，按钮墙退到「精选」和分类页里。

## 5 万级站点的硬问题（成败在这里）

### 5.1 结构：一个「主题」维度撑不住一万条

17 个主题在 189 条时是清晰的，在 10000 条时会变成 17 个塞满东西的抽屉。需要多维：

| 维度 | 例子                             | 谁来维护    |
| ---- | -------------------------------- | ----------- |
| 主题 | 新闻、AI、设计、财务             | 现在已有    |
| 任务 | 找数据、找素材、找模板、查公司   | 人工策展    |
| 角色 | 行政、HR、财务、销售、法务、研发 | 人工策展    |
| 场景 | 做周报、做竞品分析、找供应商     | 场景包      |
| 质量 | S 精选 / A 收录 / B 长尾         | 规则 + 人工 |

**验收标准**：随便给一个办公任务，能在 3 次点击内到达一个可用站点。

### 5.2 供给：一万条不可能靠 PR 手工攒

| 来源        | 规模    | 成本 | 质量             | 判定                       |
| ----------- | ------- | ---- | ---------------- | -------------------------- |
| 人工策展    | 300–500 | 高   | 最高             | 必做，是信任的来源         |
| 众包提交    | 2000+   | 中   | 中（要审核）     | 必做，是规模的来源         |
| 批量导入    | 5000+   | 低   | 低（要机器校验） | 可做，是覆盖面的来源       |
| AI 生成候选 | 不限    | 极低 | 极低（会编造）   | 只能做候选池，不能直接上线 |

我的建议：**三层分开、在界面上分开**。S 层 300 条人工策展永远出现在首页；
A 层 2000 条众包，出现在搜索与分类；B 层 5000 条导入，只出现在搜索结果，默认折叠。
**混在一层里，就是 hao123。**

### 5.3 质量信号：让「值得点」可计算

每条至少要有四个可计算字段：可访问（每日/每周探测）、最近更新频率、是否有登录墙、
是否被同类高质量站替代。现在的 `scripts/lib/checks.ts` 已经有前两个的雏形，
但只对 189 条人工跑 —— 一万条要**抽样巡检 + 自动降权**，而不是全量探测（会跑几小时）。

### 5.4 反 hao123 的机制

hao123 的问题不是「站多」，是「每个入口都不回答『什么时候用它』」。
所以 RedBot 的每一条都必须有一句**使用时机**，而不是一句公司介绍：

- 好：`查一家公司的股权和诉讼，先看这里`
- 坏：`专业的商业信息查询平台`

现有 `desc` 平均 8.5 字，方向是对的，但一万条里至少有一半写不出来 —— **写不出来的就不该进 S 层**。

## 6 与现有红线的冲突（必须选，不能糊）

| 现有红线       | v2 的冲突                  | 三个选项                                                     | 我的倾向                                  |
| -------------- | -------------------------- | ------------------------------------------------------------ | ----------------------------------------- |
| 零后端、纯静态 | 「我的」跨设备同步需要账号 | A 只本地 + 导出文件 / B 可选登录（不登录也能用）/ C 强制登录 | **B**：换电脑很常见，但登录墙会杀死新用户 |
| 单类硬顶 20 条 | 万级目录                   | A 取消上限 / B 上限只作用于 S 层 / C 全放开                  | **B**：稀缺性留在精选层，规模放在下层     |
| 只收 PR        | 众包提交量级               | A 只有 PR / B 加提交表单 / C 允许批量导入第三方目录          | **B + C**：PR 留核心，表单收长尾          |
| 单人维护       | 审核与巡检量               | A 单人 / B 招 2 位 co-maintainer / C 社区投票                | **B**（v1 就是这个结论）                  |
| 不做聚合       | 无冲突                     | ——                                                           | **保持**                                  |

## 7 三条路线

|                 | A 精选目录（现状延伸） | B 办公工作入口（推荐）           | C 浏览器默认入口       |
| --------------- | ---------------------- | -------------------------------- | ---------------------- |
| 规模            | 500 条，全人工         | 300 精选 + 2000 众包 + 5000 导入 | 同 B + 个人化          |
| 首页            | 按钮墙                 | 搜索框 + 任务入口 + 我的         | 新标签页               |
| 差异化          | 选得准                 | 知道你要做什么                   | 不用想起来打开         |
| 要放弃          | 规模、覆盖面           | 极简的美感（会变复杂）           | 「一个网页」的形态     |
| 90 天能验证什么 | 内容质量               | 搜索与任务入口是否真的省时       | 留存与日活             |
| 风险            | 叫好不叫座             | 结构做不好就是 hao123            | 扩展审核、跨浏览器成本 |

我的判断：**主线走 B，用 C 做分发**。B 解决「找得到」，C 解决「想起来」——
你说的问题（不知所以）恰好是这两件事的叠加，只做 B 会变成「又一个目录站」。

## 8 90 天（如果走 B）

### 第 1–2 周：把「我的」做出来

- 足迹升级：固定（pin）、分组、备注、导入导出 JSON；未登录也完整可用。
- PC 键盘流：`/` 聚焦搜索、`↑↓` 选择、`Enter` 打开、`Esc` 返回。

### 第 3–6 周：任务入口 + 搜索升级

- 新增「任务」维度，先做 20 个高频办公任务（找数据、找素材、找模板、查公司…），每个任务 5–10 个站。
- 搜索加拼音首字母、站点别名、同义词（fuse.js 需要预建索引，不能只靠字段匹配）。
- 现有 189 条按「使用时机」重写 `desc`，写不出来的降级。

### 第 7–10 周：分层目录 + 上线分发

- S 层手写 300 条；A 层用提交表单收 2000 条；B 层导入 + 机器校验 5000 条。
- 上线：域名、部署、新标签页（先做 PWA 的「添加到新标签页」或用扩展）。
- 加一个**可选**的匿名统计，否则无法判断任务入口是否有效。

### 第 11–12 周：复盘

- 看三个数：搜索成功率、人均固定站点数、7 日回访。

## 9 指标（不破坏隐私的前提下）

| 类型     | 指标                             | 怎么拿                                      |
| -------- | -------------------------------- | ------------------------------------------- |
| 北极星   | 7 日回访率                       | 可选匿名统计；没有统计就看固定的站数变化    |
| 输入     | 搜索后点了结果的比例（成功率）   | 本地记录 + 用户主动上报？否则只能做灰度对比 |
| 使用深度 | 人均「我的」站点数               | 只能本地统计，汇总需要用户同意              |
| 质量     | 死链率、S 层首页占比、每类条目数 | CI 直接产出，不需要用户数据                 |

诚实说：**没有统计，就只能靠定性反馈**。你要在第 10 节 Q4 里定这件事。

## 11 一句话与最大风险

**一句话**：RedBot 要回答的不是「这个网站是什么」，而是「我现在要做这件事，该去哪个网站」——
然后把这个答案留在「我的」里，下次不用再问。

**最大风险**：一万条没有结构就是 hao123。能不能守住，取决于三件事：

1. 有没有「任务」这一维（没有它，一万条只是更长的列表）
2. S 层是否真的只有几百条（混层就死）
3. 每条是否写得出「什么时候用它」（写不出就是噪音）

**第二风险**：审核与巡检跟不上，链接腐烂后用户回来一次就不再回来。
